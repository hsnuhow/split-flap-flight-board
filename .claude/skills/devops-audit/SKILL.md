# /devops-audit — 專案稽核編排

你（主控）派 `devops-auditor` 平行稽核五個維度，彙整成一份報告。

**全程唯讀。** 稽核不修東西——發現問題出報告，修不修、怎麼修由使用者決定。

## 開始前

先讀本專案的 `CLAUDE.md` 最前面的「部署口令與上線流程」節，確認：

- 本專案是**雙軌**（staging ＋ production）還是**單軌**（只有一個對外環境）
- 對應的雲端專案 id
- 若本專案有 `check-env.md`，一併讀——那裡記著上次稽核的已知問題

沒有這些資訊就不要開始，先問使用者。

## 派工

**同一回合並行派出**五個 `devops-auditor`，各給一個維度：

| # | 維度 | 重點 |
|---|---|---|
| 1 | **部署口令與上線流程** | 口令是否符合全站標準；是否有繞過口令閘的腳本；上線鐵則是否落實 |
| 2 | **文件誠實性** | 文件說有的檔案／指令／防護，是否真的存在 |
| 3 | **雲端基準線** | 備份、警示、預算、API key、私鑰、公開 IAM、rules |
| 4 | **權限設定** | `.claude/settings.json` 三段；deny 是否有洞；是否可版控 |
| 5 | **本機環境** | 金鑰檔、ADC、相依架構、測試可跑性 |

每個派工都要明確寫出：**專案路徑、雲端專案 id、單軌或雙軌、以及唯讀禁令**。

## 彙整

收齊後合併，**不要只是把五份報告貼在一起**：

1. **去重**：同一個根因在多個維度出現時合併成一項
   （例：`.gitignore` 排除 `settings.json` 會同時出現在維度 2 和 4）
2. **重排序**：跨維度依實際風險排序，不是依維度順序
3. **標出因果鏈**：獨立看是 MEDIUM、串起來是 HIGH 的組合要點出
   （例：「單軌 ＋ 有真實使用者 ＋ 無備份 ＋ 無還原口令」＝ 事故時無法復原）

## 報告格式

```
# DevOps 稽核 — <專案> — <日期>

## 一句話結論
<最該處理的一件事>

## 🔴 HIGH
每項：發現 / 證據（指令與輸出）/ 為什麼危險 / 具體處置

## 🟡 MEDIUM
## 🟢 通過（簡列，證明真的查過）
## ⚪ 無法驗證
<項目與原因。空的也要寫「無」。>

## 建議順序
<若時間有限，先做哪三件>
```

## 紀律

- **「讀不到」不等於「不存在」。** API 沒開、權限不足都算「無法驗證」。
  誤報成「沒有」會導致錯誤的補救。
- **文件宣稱的防護要實測。** 不存在的防護比沒有防護更危險。
- **給證據，不給結論。** 每項發現附上實際跑的指令與輸出。
- **不臆測。** 跑不出來就寫無法驗證與原因。
- 稽核員不得改任何東西；主控也不得在稽核流程中順手修。

## 用法

- `/devops-audit` — 完整稽核五個維度
- `/devops-audit 部署` — 只查部署口令與流程（上線前快檢）
- `/devops-audit 雲端` — 只查雲端基準線（定期健檢）

## 與其他工具的分工

| 工具 | 範圍 | 頻率 |
|---|---|---|
| `/devops-audit` | **單一專案**深度稽核，含文件與程式碼 | 上線前、接手時、每季 |
| `check-env.md` | 單一專案的一次性檢查清單 | 一次 |
| OpDev 的 `opdev scan --plan` | **跨全部專案**的雲端掃描 | 每週 |
| OpDev 的 `opdev health` | 跨專案的服務健康 | 每日 |

`/devops-audit` 查得比 `opdev` 深（會讀文件、跑測試），但只看一個專案。
兩者互補，不互相取代。
